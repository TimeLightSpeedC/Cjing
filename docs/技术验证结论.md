## 2. 🔴 新发现：可能影响 P3/P4 计划的重要事项

以下各项是本次逐文件核实新发现的，**路线图 ProMax 尚未反映**，需在对应阶段开工前修订。

### 2.1 HarmonyOS：必须用鸿蒙自带 CMake，标准 CMake 无法识别该平台

> 官方原文：*"you **must** use the CMake that comes with HarmonyOS's development tools, or building will fail, as standard CMake does not recognize this platform at all currently."*

**影响**：P4-T5 不能沿用桌面/移动的 CMake 配置方式，需显式指定：
```
$CLT/sdk/default/openharmony/native/build-tools/cmake/bin/cmake \
  -DCMAKE_TOOLCHAIN_FILE=$CLT/sdk/default/openharmony/native/build/cmake/ohos.toolchain.cmake \
  -DOHOS_COMPATIBLE_SDK_VERSION=16.0.0
```
**推论**：CI 上构建鸿蒙也必须用鸿蒙的 CMake，这与"CLion 自带 CMake 4.3.1 通用"的假设**在鸿蒙端不成立**。

### 2.2 HarmonyOS：必须以官方 `openharmony-project` 为模板，不能新建工程

> 官方原文：*"Do not create a new project in DevEco Studio, since there are pieces of ArkTS scripting that need to be set up correctly for SDL, and that code is already present in openharmony-project."*

**影响**：P4-T2 从"创建 DevEco 工程"改为"复制 SDL 源码树中的 `openharmony-project` 并按需改名"。这条若做错，会在 NAPI/XComponent 对接上反复踩坑。

### 2.3 HarmonyOS：必须产出 `libmain.so`（共享库），**不得构建可执行文件**

> 官方原文：*"Your app **must** compile to a shared library named "libmain.so"... Do not build an executable! It must be a shared library, due to how HarmonyOS deals with apps."*

**影响**：我们的 `CjingApp` 是**可执行文件**（桌面/移动形态）。鸿蒙端需要**另一套目标形态**：
`add_library(main SHARED <sources>)`。这与 Android（`libmain.so`）方向一致，但**桌面可执行文件不能直接复用**。
→ 需要在 CMake 中为鸿蒙/Android 增加"库形态"的目标分支。

### 2.4 HarmonyOS：`SDL_AppIterate` 由 XComponent 的 OnFrame 回调驱动，不是自由循环

> 官方启动时序：*"whenever the XComponent fires its OnFrame callback, we will call `SDL_OpenHarmonyOnFrameCallback()`, which calls libmain.so's `SDL_AppIterate()`"*

**影响**：帧驱动模型与桌面不同（尤其 **P2-T20「仅在状态变化时 present」** 在鸿蒙上语义仍在，但要确认 OnFrame 的触发频率）。
P4 需实测帧节奏，不能假设与桌面一致。

### 2.5 HarmonyOS：`SDL_HINT_ORIENTATION` 尚未实现

> 官方原文（位于 STILL TODO 列表）：*"`SDL_HINT_ORIENTATION` (for runtime control; but you _can_ explicitly set the "orientation" setting in module.json5 for now if you need a specific global, unchanging setting.)"*

**影响**：路线图 P3-T1/P3-T6 提到"屏幕方向"。**桌面/移动端**方向策略可运行时控制；
**鸿蒙端**只能在 `module.json5` 里设**静态**方向。三端的"方向策略"需分开表述。

### 2.6 iOS/macOS 最低版本：官方文档与官方工程模板不一致（已查明口径）

| 项 | 官方 docs/ 说法 | 官方 Xcode 工程模板 | **本项目采用** |
|----|----------------|-------------------|---------------|
| iOS | 可部署到 **iOS 11.0** 及更新 | `IPHONEOS_DEPLOYMENT_TARGET = 15.0` | **iOS 12.0**（折中：低于模板值以获得设备覆盖，高于文档下限以留安全余量）|
| macOS | 可部署到 **macOS 10.13** 及更新 | `MACOSX_DEPLOYMENT_TARGET = 12.0` | **macOS 12.0**（跟随官方模板，避免与模板行为不一致）|

**口径说明**：模板值代表"SDL 官方自己构建 framework 时用的目标"，文档值代表"SDL 支持的下限"。
项目取值落在两者之间是合理的，但**必须写清依据**，避免后续误判为配置错误。

### 2.7 官方文档存在一处笔误（务必以头文件为准）

`docs/README-harmonyos.md` 写 *"use the main callbacks (with `#define SDL_USE_MAIN_CALLBACKS`)"*，
但**头文件中定义的宏是 `SDL_MAIN_USE_CALLBACKS`**（`include/SDL3/SDL_main.h:99`），
全源码中**不存在** `SDL_USE_MAIN_CALLBACKS`。

**影响**：若照文档写，宏不会被识别 → 会退化为"需要提供 `main()`"的路径，且**不会报错**，属于静默失效。
本项目 `platform_sdl/main_callbacks.cpp` 使用的是正确宏名。

### 2.8 HarmonyOS 实测状态（官方自述）

> 官方原文：*"All testing to date has been done on a real phone, a Huawei Mate 80. SDL currently supports HarmonyOS 5.0.4 (API level 16) and later, although low-end testing hasn't been done"*

**结论**：官方支持的起点是 **HarmonyOS 5.0.4 / API 16**，且**真机验证机型单一（Mate 80）**、未做低端设备测试。
这印证了路线图"风险等级 = 中（可用但未经充分实战）"的判断，**并且应当把 API 16 作为硬性下限写入 P4**。

### 2.9 HarmonyOS 其他可用能力与限制（供 P4 设计参考）

| 项 | 状态 |
|----|------|
| 窗口 | **同一时刻只允许一个 `SDL_Window`**，且占满整个显示（类 Android） |
| 全屏 | 全屏会隐藏系统状态栏与导航栏；非全屏则保留 |
| 渲染 | OpenGL ES 3 与 Vulkan 均可用；2D 渲染器优先走 GLES2；**桌面版 OpenGL 在 SDL 内被禁用** |
| 音频 | 走 **OHAudio** 后端（OpenSL ES 未使用） |
| 录音权限 | 需 `ohos.permission.MICROPHONE`；**被拒绝后不会再弹窗**，需引导用户去系统设置 |
| 剪贴板读取 | 需 `ohos.permission.READ_PASTEBOARD`（**受限权限**：需向华为申请） |
| 触摸 | 支持，且**支持多点触控** |
| 文件系统 | `SDL_GetBasePath()` **无条件返回 `"assets://"`**；`SDL_GetPrefPath()` 落在应用私有目录 |
| 平台宏 | 定义 `SDL_PLATFORM_OPENHARMONY` 与 `SDL_PLATFORM_UNIX`；**不**定义 `SDL_PLATFORM_LINUX` |
| 动态 API | 该平台**禁用** Dynamic API |
| 日志 | `SDL_Log()` 走 hilog，用 `hdc hilog \| grep -F <bundleName>` 查看；**release 版用户也能看到日志**，注意不要打印敏感信息 |

## 5b. SDL3_ttf 接入实测（2026-10-15 补充）

| 项 | 结论 |
|----|------|
| 版本 | SDL3_ttf **3.3.0** |
| **关键配置** | **必须 `SDLTTF_VENDORED=ON`** |
| 失败现象（未启用时） | `Could NOT find Freetype (missing: FREETYPE_LIBRARY FREETYPE_INCLUDE_DIRS)`；harfbuzz 同样找不到 |
| 原因 | 未启用 vendored 时 SDL3_ttf 会去找**系统** FreeType/HarfBuzz；macOS/Windows 默认没有，鸿蒙/Android 更不会有 |
| 启用后输出 | `Using vendored harfbuzz library` / `Using vendored freetype library`，backends: harfbuzz freetype |
| 子模块 | `external/{freetype,harfbuzz,plutosvg,plutovg}`，均为 **libsdl-org 维护的补丁分支**；克隆必须 `--recurse-submodules` |
| 本项目裁剪 | `SDLTTF_PLUTOSVG=OFF`（省掉彩色 emoji 依赖，缩小鸿蒙交叉编译面） |
| 实测字体 | Noto Sans SC（SIL OFL 1.1，可随包分发）；Apple 系统中文字体**不可再分发**，故未采用 |
| 运行验证 | `[Cjing] 字体已加载: assets/fonts/NotoSansSC-Regular.ttf @ 39pt`（= 44 逻辑单位 × 0.884 输出缩放） |
| CI 验证 | 四矩阵（含 Windows）全部通过，TTF 构建三平台可用 |

> ⚠️ **注意第三方警告**：harfbuzz 源码自带若干 `-Wformat` / `-Wnontrivial-memcall` 警告，非本项目代码。
> 本项目 `core/` 与 `platform_sdl/` 保持零警告（`-Wall -Wextra -Wpedantic`）。

## 5c. 主循环节流（2026-10-17 补充，重要踩坑）

| 项 | 内容 |
|----|------|
| 现象 | 应用启动后**任何操作都出现 macOS 彩虹圈（无响应）** |
| 定位手段 | 在 `SDL_AppIterate` 内加帧计数埋点，8 秒内记录到 **163 万次**调用（约 20 万 fps） |
| 根因 | 初版实现"仅在状态变化时 `SDL_RenderPresent`"，`dirty_` 变 false 后**不再 present**；SDL 的 vsync 节流发生在 `SDL_RenderPresent` 内部，不调用它就没有任何阻塞点，主循环满速空转，事件被饿死 |
| 修复 | **内容**按需重绘，**`SDL_RenderPresent` 每帧无条件调用** |
| 教训 | "只在需要时 present"是**错误的优化** —— 它同时破坏了帧率节流与事件响应性 |
| 防回归 | 新增无界面自测 `CjingSelfTest`（覆盖渲染一帧、9 格坐标往返、事件队列排空），可纳入 CI |

## 5d. 双缓冲导致的"黑屏 + 偶发闪烁"（2026-10-17 补充，重要踩坑）

| 项 | 内容 |
|----|------|
| 现象 | 窗口**黑屏**；连续点击时偶尔闪出几个残缺图形 |
| 根因 | 渲染器是**双缓冲**。代码在 `dirty_` 为 false 时跳过 `beginFrame()`（含清屏）与全部绘制，却仍每帧 `present` → 每帧交换到另一块后备缓冲，present 的是空白/陈旧缓冲，于是窗口在"有内容/黑屏"之间交替 |
| 修复 | **每帧全量重绘 + 每帧 present**。井字棋只有几十条绘制指令，全量重绘代价可忽略 |
| 教训 | "只在状态变化时重绘"**在双缓冲下不成立**；若确需按需重绘，必须渲染到**持久化离屏纹理**再整帧贴出，不能直接跳过绘制 |
| 配套修复 | `drawX` 加粗原沿对角线方向偏移（导致笔画粗细不均、交叉点错位）→ 改为沿**法线**方向偏移；`drawO` 折线段数与笔宽同步加大 |
| 防回归 | 自测新增**像素级**检查：渲染到离屏纹理后 `SDL_RenderReadPixels` 读回，统计非背景像素数（实测 1465），确保"画面确有内容"而非仅"未崩溃"；并支持 `CJING_SHOT=<path>` 导出画面供人工核对 |

> **可视化验证方法**：`CJING_SHOT=/path/shot.bmp ./build-ttf/bin/CjingSelfTest`
> 会导出三张图（棋盘、获胜局面、含中文 HUD），已用此方法确认：
> 棋盘网格正确、X 对称、O 圆环闭合、获胜连线高亮、**中文文字渲染正常无方框**。
