1. **必须显式指定鸿蒙自带的 ninja**：它不在 PATH，且**不能**用系统/CLion 的 ninja 顶替 —— configure 会报

## 三、HarmonyOS PC 多窗口适配：可行但受 SDL3 硬限制

### 3.1 🔴 硬性事实：SDL3 的鸿蒙后端**只支持一个窗口**

这不是我的推测，是源码里的**显式限制**：

```c
// src/video/openharmony/SDL_openharmonywindow.c:42
// Currently only one window
SDL_Window *OPENHARMONY_Window = NULL;

// :54
if (OPENHARMONY_Window) {
    result = SDL_SetError("SDL on OpenHarmony (currently) only supports one window");
    goto endfunction;
}
```

视频后端还有一处直接假设单窗口：`SDL_openharmonyvideo.c:83` 无条件向 `OPENHARMONY_Window` 发送 resize 事件。

**含义**：创建第二个 `SDL_Window` 会**直接失败并返回错误**。所以在**不改 SDL 源码**的前提下，
HarmonyOS 端不可能有多个 SDL 窗口。同一限制也适用于 Android（SDL 在移动端一向如此）。

### 3.2 HarmonyOS PC 的窗口形态（官方概念，供适配设计）

HarmonyOS 应用窗口有若干形态：**全屏、分屏、自由窗口（freeform）、悬浮窗**。
在 PC 上应用会以**自由窗口**运行 —— 用户可任意拖拽、缩放窗口尺寸。
官方为此提供的适配手段是**栅格断点响应式布局**（按窗口宽度断点切换布局），
参见 [窗口模式（官方最佳实践）](https://developer.huawei.com/consumer/cn/doc/best-practices/bpta-multi-device-window-mode) 与
[应用适配自由窗口](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/application-adaptation-freeform-window)。

> ⚠️ 这两份官方文档是 JS 渲染的，我无法抓取正文核对细节；
> 上述为概念层面的可靠信息，**具体断点数值需你在浏览器中打开确认**。

### 3.3 对我们这个井字棋意味着什么

**关键判断：单窗口对我们几乎无损。**

井字棋是单窗口游戏 —— 不需要同时开两个游戏窗口。而 PC 上的核心需求是
"**窗口被用户任意缩放时，棋盘始终正确**"，这恰好是我们在 P0/P1 已经建立的架构能力：

| 能力 | 我们的实现 | 对 PC 自由窗口的意义 |
|------|-----------|-------------------|
| 逻辑分辨率 + letterbox | `SDL_SetRenderLogicalPresentation`（P2-T2） | 窗口任意宽高比都不变形 |
| 布局模型只吃逻辑尺寸 | `Layout`（已实现 + 单测覆盖） | 缩放时棋盘自动重算居中 |
| 每格中心往返映射 | `layout.cpp`（有测试） | 缩放后点击命中仍准确 |
| 安全区注入 | `SDL_GetWindowSafeArea`（P2-T11） | PC 窗口标题栏/三键不遮挡内容 |
| 仅状态变化时 present | `dirty_` 标志（已实现） | 自由窗口拖动时不空转耗电 |

**唯一缺口**：`Layout::compute` 目前按"逻辑尺寸正方形 + 安全区"计算，
**没有响应式断点**概念。PC 窗口被拉成很扁或很窄时，棋盘会缩得很小（正确但不好看）。

### 3.4 建议：把"多窗口"拆成三个层次，只做前两层

| 层次 | 内容 | 是否建议 | 工作量 |
|------|------|---------|--------|
| **L1 单窗口自适应**（真正的 PC 适配） | 窗口任意缩放/宽高比下布局正确；加宽高比断点（如极端扁窗口时把状态文字移到侧边） | ✅ **建议做** | 小，`Layout` 已具备基础 |
| **L2 多设备形态** | 手机/平板/PC 三形态的断点与边距策略（PC 上棋盘可用更大比例） | ✅ **建议做** | 小，纯逻辑，可单测 |
| **L3 真正多窗口** | 同时开多个 SDL 窗口（如"主窗口 + 独立设置窗"） | ❌ **不建议** | 大：需 fork SDL3 的鸿蒙后端（`SDL_openharmonywindow.c` 仅 187 行，技术上可行），但会脱离官方版本、增加鸿蒙维护成本，且对本游戏无收益 |

**如果将来确实需要 L3**，有两条路：
- **Fork SDL3 鸿蒙后端**：把单窗口全局改造成窗口列表。后端体量小（video 280 行 + window 187 行），
  但意味着长期维护自己的 SDL 分支，与我们"六端共用同一 commit SHA"的原则冲突。
- **鸿蒙端改用路线 B**（ArkTS + XComponent + NAPI + 自绘渲染），由 ArkTS 侧管理多个窗口/页面。
  这本就是路线图里保留的退路，代价是放弃 SDL 的跨平台复用。

### 3.5 需要补的验证（P4 阶段）

- [ ] PC 自由窗口拖拽缩放时的**帧驱动行为**：鸿蒙的 `SDL_AppIterate` 由 XComponent 的 OnFrame 回调驱动，
      拖动窗口时该回调是否持续触发？若不触发，"仅状态变化时 present"是否需要调整
- [ ] 窗口尺寸变化事件在 PC 自由窗口下的**触发频率与时机**
- [ ] 安全区在 PC 窗口形态下（标题栏 + 三键）的实际 insets 值
- [ ] 极端宽高比（如 300×900 竖长窗）下棋盘的可用性下限
