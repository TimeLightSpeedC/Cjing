# 构建流程对比：本项目的 CMake-first 方案 vs SDL 官方工程方案

> 用途：解释"桌面 / Android / iOS 分别是怎么跑起来的"，
> 以及我们为什么没有照搬官方模板，方便你判断何时该切换。
>
> 对应代码：根 `CMakeLists.txt`、`cmake/`、`android/`、`ios/`

---

## 一、总体结构：一份源码 + 三个"胶水层"

```
                 ┌──────────────────────────────┐
                 │  core/       纯逻辑，零平台依赖 │
                 │  game / layout / io / text/tap │
                 └──────────────┬───────────────┘
                                │ 只依赖接口（IView/IAudio/IAssetIO/ISaveIO）
                 ┌──────────────┴───────────────┐
                 │  platform_sdl/  SDL 实现层     │
                 │  app / main_callbacks / view  │
                 │  io / audio                   │
                 └──────────────┬───────────────┘
          ┌─────────────────────┼─────────────────────┐
          │                     │                     │
   ┌──────┴──────┐      ┌───────┴───────┐     ┌───────┴───────┐
   │ 桌面(3 平台) │      │    Android    │     │      iOS      │
   │ CMake+Ninja │      │ Gradle+CMake  │     │ CMake+Ninja   │
   │ 可执行文件   │      │ libmain.so    │     │ .app 静态链接  │
   └─────────────┘      └───────────────┘     └───────────────┘
```

核心不变，变的是"谁来编译、产物长什么样、系统怎么加载它"。

## 二、桌面流程（Windows / macOS / Linux）

### 步骤

```bash
cmake -S . -B build -G Ninja          # 配置：解析依赖
cmake --build build                   # 编译
ctest --test-dir build --output-on-failure   # 单元测试
./build/bin/CjingSelfTest             # 无界面自测（字体/存档/坐标）
./build/bin/CjingApp                   # 跑起来看画面
```

### 依赖是怎么来的（`cmake/CjingDeps.cmake`）

优先用**本地缓存**，避免每次重新下载：

```cmake
cjing_detect_dep(SDL3 CJING_SDL3_SOURCE_DIR
    "${CJING_CACHE_DIR}/sdl3-src"
    "${CJING_CACHE_DIR}/sdl3probe/build/_deps/sdl3-src")
```

命中缓存 → 设置 `FETCHCONTENT_SOURCE_DIR_SDL3` + `UPDATES_DISCONNECTED`；
未命中 → FetchContent 联网下载（`CJING_OFFLINE=ON` 时直接报错，不允许偷偷联网）。

### 验证手段（三层）

| 层 | 手段 | 能发现什么 |
|---|---|---|
| 单元测试 | Catch2，248 断言 | 游戏规则、布局数学、存档序列化、文案表、双击判定 |
| 自测 | `CjingSelfTest`（离屏渲染） | 字体字形覆盖、文字缩放、坐标换算、存档往返、事件队列不死循环 |
| 人工/CI 截图 | `SDL_RenderReadPixels` 导出 PNG | 画面是否真的对（CI 会比对/上传） |

> CI 盲区（已在文档中记录）：CI 用离屏纹理按 scale=1 渲染 900×900，
> **缩放相关的 bug 在 CI 上看不出来**，必须在真机/高 DPI 环境验。

## 三、Android 流程

### 三个角色

```
Gradle (Java)  ──externalNativeBuild──▶  CMake (C/C++)
     │                                        │
     │ 打包 APK                                │ 产出 libmain.so / libSDL3.so / libSDL3_ttf.so
     ▼                                        ▼
  APK = 代码 + assets/ + lib/<abi>/*.so
     │
     ▼
 SDLActivity (Java)  ──System.loadLibrary──▶  dlopen("libmain.so") → dlsym("SDL_main")
```

### 为什么必须是 `libmain.so`（共享库）

- Android 应用进程由 Zygote fork 而来，**不能直接 exec 一个 ELF 可执行文件**；
  只能 `dlopen` 一个 `.so`。
- SDL 的 Java 层 `SDLActivity` 启动一个线程，调用 `nativeRunMain`，
  里面 `dlopen` + `dlsym("SDL_main")`。
- 我们的入口是 `SDL_MAIN_USE_CALLBACKS` 模式，`SDL_main.h` 里有一行
  `#define main SDL_main`，所以 `libmain.so` 导出的正是 `SDL_main`。

```cmake
# android/app/jni/CMakeLists.txt
add_library(main SHARED ...)          # 名字必须是 main → libmain.so
target_link_libraries(main PRIVATE SDL3::SDL3 SDL3_ttf::SDL3_ttf)
```

### 资源为什么是 `assets://`

APK 里的 `assets/` 不是文件系统路径，而是压缩包内的条目。
SDL 用 `AAssetManager` 读它，并对外暴露成 `assets://` 前缀：

```c
// SDL3 源码：Android 的 base path
char *SDL_SYS_GetBasePath(void) { return SDL_strdup("assets://"); }
```

所以资源路径是 `assets://fonts/xxx.ttf`，
**不能**再插一层 `assets/`（会变成 `assets:///assets/...`）。

> 这一条曾经是路线图里的错误记录（"Android 返回 ./"），已在实测后修正。

### 验证闭环

```bash
./gradlew assembleDebug
adb install -r app-debug.apk
adb shell am start -n com.timelightspeed.cjing/.MainActivity
adb logcat -s SDL:V                 # 看 [Cjing] 日志
adb exec-out screencap -p > s.png   # 看画面
adb shell run-as com.timelightspeed.cjing cat files/save.txt   # 看存档
```

**存档内容是权威判据**：`TTT1,XO.......,X,2` 这种字符串能证明"到底落了几子、轮到谁"，
比数像素可靠（像素统计踩过 BMP 通道顺序的坑）。

## 四、iOS 流程（我们现在的方案）

### 与官方最大的不同：不用 xcframework

```bash
cmake -S ios -B build-ios-sim -G Ninja \
  -DCMAKE_SYSTEM_NAME=iOS \
  -DCMAKE_OSX_SYSROOT=iphonesimulator \
  -DCMAKE_OSX_ARCHITECTURES=arm64 \
  -DCMAKE_C_COMPILER="$(xcrun -find clang)" \
  -DBUILD_SHARED_LIBS=OFF
cmake --build build-ios-sim          # → build-ios-sim/cjing.app
```

产物是 `.app`，里面直接是 Mach-O 可执行文件 + `assets/`，
SDL3 / SDL3_ttf 都是**静态链接**进去的。

### 验证闭环

```bash
xcrun simctl boot "iPhone 17 Pro"
xcrun simctl install booted build-ios-sim/cjing.app
xcrun simctl launch booted com.timelightspeed.cjing
xcrun simctl io booted screenshot /tmp/ios.png
xcrun simctl spawn booted log show --last 1m \
  --predicate 'processImagePath CONTAINS "cjing"'    # 看 SDL_Log
```

### iOS 特有的三个坑（都已踩过）

| 坑 | 现象 | 处理 |
|---|---|---|
| `SDL_opengl.h` 在 iOS 为空 | SDL_ttf 的 GL 文本引擎编译失败（`GLuint` 未定义） | 从目标源列表剔除该文件（只用 surface 渲染） |
| 安全区单位 | `SDL_GetWindowSafeArea` 返回**点**，呈现矩形是**像素** → 内缩算成负数，棋盘 0×0 | 先按 `ppu = 呈现宽/窗口宽` 换算 |
| HiDPI 文字发糊 | `SDL_GetRenderScale` 恒为 1.0，不是像素/逻辑比 | 改用逻辑呈现宽度 / 逻辑宽 |

## 五、SDL 官方工程方案（供你对比研究）

### 5.1 官方 Android 模板

结构（与本项目同源）：

```
android-project/
├── app/
│   ├── build.gradle            # externalNativeBuild { cmake { path 'jni/CMakeLists.txt' } }
│   ├── src/main/java/org/libsdl/app/*.java   # SDLActivity/SDLSurface/...（约 12 个文件）
│   ├── src/main/AndroidManifest.xml          # activity 指向 SDLActivity 或其子类
│   └── jni/CMakeLists.txt                    # add_subdirectory(SDL) + add_subdirectory(src)
```

与本项目的差异仅仅是我们把 `jni/CMakeLists.txt` 换成了自己的源码列表。

### 5.2 官方 iOS 方案（xcframework）

摘自 `docs/README-ios.md`：

1. 打开 `Xcode/SDL/SDL.xcodeproj`，构建 **`SDL3.xcframework`** 目标；
2. Xcode 新建 **iOS Game 模板**工程（Objective-C + Metal）；
3. 把 `SDL3.xcframework` 拖进 *Frameworks, Libraries, and Embedded Content*；
4. 设置为 **Embed & Sign**；
5. 源文件里 `#include <SDL3/SDL_main.h>`；
6. Info.plist 必须有 **`UILaunchScreen`** 键，否则系统按兼容模式跑、分辨率受限；
7. 分发前：**用脚本移除嵌入的 framework**（否则 Archive 会失败）。

> 官方文档原文（line 65）：
> "Embedding the SDL3 Xcode project makes SDL3.framework a target of your app,
> so it will be included in the archive... As this prevents successful distribution,
> remove the framework via a script in the Build Phase after the Embed & Sign step."

### 5.3 xcframework 是什么、为什么需要它

一个 `.xcframework` 目录里打包了**多份 .framework**：

```
SDL3.xcframework/
├── ios-arm64/                     # 真机
├── ios-arm64_x86_64-simulator/    # 模拟器（Intel + Apple Silicon）
└── Info.plist                     # 声明"哪个平台用哪份"
```

Xcode 按当前构建目标自动挑一份。它解决的是"**分发预编译二进制**"的问题：
用户不必自己编译 SDL。

### 5.4 Embed & Sign 是什么

Xcode 把 framework 复制进 `.app/Frameworks/` 并用你的证书签名。
App Store 要求**所有嵌入的动态库都已签名**，所以苹果强制这一步。

静态链接（本项目的做法）没有嵌入物，也就不存在这个步骤。

## 六、两种方案对比

| 维度 | 本项目（CMake-first，源码） | 官方（xcframework + Xcode 工程） |
|---|---|---|
| 依赖形态 | 源码，随项目一起编译 | 预编译二进制 |
| 构建入口 | CMake / Ninja，命令行 | Xcode 工程（.xcodeproj） |
| 三平台一致性 | 同一套 CMake 逻辑 | 每平台一套工程 |
| CI 友好度 | 高（无需 GUI） | 中（工程文件 + 签名设置） |
| 升级 SDL | 改一个 SHA，重新编译 | 重新下载 xcframework |
| 分发前处理 | 无（静态链接） | **必须移除嵌入的 framework** |
| 断点调试 SDL 内部 | 可以（源码就在本地） | 可以（需 dSYM） |
| 上手成本 | 需要懂 CMake 工具链 | 熟悉 Xcode 即可 |
| 体积 | 只编译用到的源文件 | 整包预编译库 |

---

## 七、我们为什么选现在这条

1. **可复现**：三平台用同一份源码、同一 SHA，CI 能验证；
2. **无 GUI 依赖**：CI 与我这边的沙箱都能跑（Xcode 工程 + DerivedData 反而受限）；
3. **避开 T19 的负担**：静态链接没有"嵌入 framework 再移除"这一步；
4. **调试穿透**：SDL 源码在本地，断点能直接进 SDL 内部；
5. **教学价值**：整条链路是显式的，适合理解每个平台到底发生了什么。

## 八、什么时候应该切到官方方案

- 团队以 Xcode 为主，需要 Interface Builder / SwiftUI 混合开发；
- 需要稳定上架 App Store，且不想自建 iOS 构建链；
- 需要使用 SDL 官方模板里的 Metal 示例；
- 希望减少自己维护构建脚本的成本（接受工程文件带来的不透明）。

> 两条路并不冲突：`core/` 与 `platform_sdl/` 是干净的，
> 切到 xcframework 时只需替换"怎么把源码编进 app"这一层。

## 八点五、为什么 Android 产出多个 `.so`，iOS 只有一个可执行文件

### Android：不得不动态

| 约束 | 说明 |
|---|---|
| 进程模型 | 应用跑在 ART 虚拟机里，**不能 exec 一个 ELF 可执行文件**（SELinux + 应用沙箱都不允许） |
| 加载机制 | 只能 `dlopen` 一个 `.so` 进同一进程 |
| SDL 的约定 | `SDLActivity` → `nativeRunMain` → `dlopen("libmain.so")` → `dlsym("SDL_main")` |
| 打包机制 | APK 的 `lib/<abi>/*.so` 安装时解包到 `nativeLibraryDir`，按 ABI 选择 |

所以 Android 必然产出多份动态库（每个 ABI 各一套）：

```
lib/arm64-v8a/libmain.so        ← 我们的代码
lib/arm64-v8a/libSDL3.so
lib/arm64-v8a/libSDL3_ttf.so
lib/x86_64/...                  ← 模拟器用
```

### iOS：可以也应当静态

| 约束 | 说明 |
|---|---|
| 进程模型 | app 本身就是 `.app` 里的 Mach-O 可执行文件，由 dyld 加载 |
| 动态库限制 | 嵌入的动态库必须签名；且不允许下载代码后动态执行 |
| 分发 | 嵌入 framework 会在 Archive 时被带上，官方要求**打包前移除** |

静态链接把 SDL3 / SDL3_ttf 直接合并进可执行文件，产物只有一个 `cjing`：

```
cjing.app/
├── cjing            ← 所有代码都在这里（otool -L 只看到系统框架）
├── Info.plist
└── assets/
```

### 关键 CMake 开关：`BUILD_SHARED_LIBS=OFF`

SDL3 的默认行为（源码 `CMakeLists.txt:233`）：

```cmake
if(SDL_SHARED_DEFAULT AND SDL_STATIC_DEFAULT AND SDL_SHARED_AVAILABLE)
  if(DEFINED BUILD_SHARED_LIBS)
    if(BUILD_SHARED_LIBS) → 只建动态库
    else                  → 只建静态库    ← 本项目
  else
    → 只建动态库
```

因此：

| 平台 | 参数 | 产物 |
|---|---|---|
| 桌面 | 默认（不设 BUILD_SHARED_LIBS） | `libSDL3.dylib/.so/.dll` + 可执行文件 |
| Android | 不设（必须动态） | 多个 `.so` |
| **iOS** | **`-DBUILD_SHARED_LIBS=OFF`** | `libSDL3.a` + `libSDL3_ttf.a` → 全部链进 `cjing` |

> 不设这个参数，iOS 上 SDL3 会生成 dylib，就得面对
> "Embed & Sign → Archive 前再移除"的完整流程。

## 八点六、宿主模型：为什么 Android 多一个 `libmain.so`

### 一句话

> **Android 的宿主不是你写的；iOS 的宿主就是你写的。**

| | 谁创建进程 | 你的代码形态 | 入口在哪里 |
|---|---|---|---|
| **Android** | Zygote fork → **ART 虚拟机** | `.so`（插件） | Java 预加载 `libmain.so` → 原生 `dlopen` 取句柄 → `SDL_main` |
| **HarmonyOS** | Ability → **ArkTS 运行时** | `.so`（插件） | ArkTS `import 'libSDL3.so'` → SDL `dlopen("libmain.so")` → `SDL_App*` |
| **iOS** | launchd **exec 你的 Mach-O** | 可执行文件本身 | `main()` 就在你的代码里 |

打个比方：

```
Android：你写的 C++ 是"租客"——房子（进程/窗口/生命周期）是系统给的 Java 框架
iOS：    你写的 C++ 是"房东"——进程就是你自己，SDL 只是请来的"管家"（framework）
```

### APK 里根本没有可执行文件

```
classes.dex / classes2.dex          ← Java 字节码（"壳"在这里）
lib/arm64-v8a/libmain.so            ← 你的 C++（502 KB）
lib/arm64-v8a/libSDL3.so            ← 引擎（3.9 MB）
lib/arm64-v8a/libSDL3_ttf.so        ← 字体（4.3 MB）
```

`libmain.so` 的依赖与导出（`llvm-readelf` 实测）：

```
DT_NEEDED: libSDL3_ttf.so, libSDL3.so, libm, libdl, libc
导出:      SDL_main, SDL_AppInit
```

它**依赖** SDL，而不是 SDL 的一部分 —— 它就是你自己的代码。

### 为什么 Android 不能把入口做成"厚壳可执行文件"

| 原因 | 说明 |
|---|---|
| 入口固定 | 应用入口永远是 `ActivityThread.main()`（Java），由 Zygote fork 后运行 |
| 没有落点 | APK 里没有"可执行文件"这个位置，系统也不会 exec 它 |
| 上下文 | 窗口、权限、生命周期、输入分发全绑定在 ART 的框架对象上 |

### 反例恰好证明这条：NDK 的 NativeActivity

```c
void android_main(struct android_app* app) { ... }   // 看起来像"纯 C 入口"
```

实际上是：

```
Java 的 android.app.NativeActivity     ← 依然是 Java 类，依然由系统创建进程
        └─ 加载 libmain.so，调用 android_main
```

**入口仍在 Java 侧**，C 代码依然是被加载的插件。

### iOS 能不能反过来"插件化"？能

Unity 的 iOS 包就是这个结构：

```
Unity-iPhone.app/
├── Unity-iPhone                          ← 薄壳可执行文件（几乎只有 loader）
└── Frameworks/UnityFramework.framework   ← 业务代码
```

于是四种组合都成立：

| 组合 | 例子 | 入口位置 |
|---|---|---|
| iOS 厚壳（静态） | **本项目** | 可执行文件（含全部代码） |
| iOS 薄壳 + framework | Unity | 可执行文件（薄） |
| Android Java 壳 + .so | **本项目** | Java（dex） |
| Android NativeActivity + .so | NDK 示例 | Java（NativeActivity） |

**规律**：iOS 的入口始终在可执行文件里；Android 的入口始终在 Java 字节码里。
变的只是"你的 C++ 放在哪一格"。

### 边界情况：Android 能执行自己带的二进制吗

能，但那是**子进程**，不是应用入口：

```
主进程（ART）──fork/exec──> ELF 子进程（如 ffmpeg CLI）
```

`nativeLibraryDir` 里的文件带执行位，Termux 之类的应用就这么做。
但 UI、生命周期仍在 ART 主进程；且 Google Play 对"下载并执行代码"有明确限制，
预置二进制也属灰色地带。

## 八点七、三平台启动链路与 `dlopen` 语义（源码级取证）

> 本节回答三个问题：
> 1. 三个平台的启动调用链各自长什么样？
> 2. 为什么 Android 要**提前**用 Java 加载 `libmain.so`？
> 3. `dlopen` 在 Android 与鸿蒙上是不是两套实现？

### 8.7.1 iOS：链接期，没有运行期查找

```
launchd exec 你的 Mach-O
  └─ dyld 加载依赖（静态链接时无依赖）
       └─ main() → SDL_RunApp → SDL_AppInit / Iterate / Event / Quit
```

- 产物：**单个 Mach-O 可执行文件**，`build-ios-sim/cjing.app/cjing`
- SDL3 / SDL3_ttf / core 全部**静态链接**进去
- **没有 `dlopen`，没有 `dlsym`** —— 所有符号在链接期解析
- 可选变体：SDL 作为 framework（Unity 那种），由 **dyld** 加载，仍不是应用自己 `dlopen`

### 8.7.2 Android：Java 预加载 + 原生 `dlopen` 取句柄

```
① System.loadLibrary("SDL3")            SDLActivity.getLibraries():
                                          new String[] { "SDL3", "main" }
② System.loadLibrary("main")              加载 main 及其 NEEDED 依赖
③ Java → nativeRunMain("libmain.so", "SDL_main")
       → dlopen("libmain.so")   // 已加载 → 返回同一句柄
       → dlsym("SDL_main")      // 调用
④ SDL_main() → SDL_RunApp() → SDL_App* 回调
```

**实测依赖与符号**（本仓库构建产物）：

```
libmain.so  DT_NEEDED: libSDL3_ttf.so, libSDL3.so, libm, libdl, libc
导出符号:              SDL_AppEvent / SDL_AppInit / SDL_AppIterate / SDL_AppQuit
                      SDL_main          ← Android 有
```

#### 为什么 Android 要提前加载 `main`？

| 原因 | 说明 |
|---|---|
| **加载顺序** | `libmain.so` 的 `DT_NEEDED` 里有 `libSDL3.so`，所以 SDL3 必须先就绪 |
| **`System.loadLibrary` 是受支持的加载路径** | 按应用 `nativeLibraryDir` 解析路径；处理 `extractNativeLibs` 的解压；执行库的静态初始化 / `JNI_OnLoad` |
| **命名空间登记** | bionic 的 linker namespace 按"谁加载"决定可见性；Java 加载会把库登记进应用的 classloader 命名空间 |
| **ReLinker 兼容层** | `SDL.java:92` 先尝试 ReLinker，解决"库很多时 Android 原生加载器 bug"，失败再回退 `System.loadLibrary` |
| **之后 `dlopen` 只是取句柄** | POSIX 保证对已加载对象再次 `dlopen` 返回同一句柄（引用计数 +1） |

**如果 Java 不预加载会怎样？** 原生 `dlopen("libmain.so")` 在应用命名空间内通常也能按名找到并加载，
但那依赖 bionic 的路径解析细节；SDL 选择显式预加载以保证**确定性**，并允许应用在
`getLibraries()` 里按顺序追加依赖（如 `SDL3_image`）。

### 8.7.3 HarmonyOS：NAPI 模块 + SDL 单次 `dlopen`

```
① ArkTS: import sdl from 'libSDL3.so'
       └─ .so 构造函数 SDL_RegisterNativeInterfaces
          → napi_module_register({ .nm_modname = "SDL3" })   SDL_openharmony.c:1196-1205
② sdl.provideArkTSObjects(this, ...)          EntryAbility.ets:49
③ 系统 onWindowStageCreate → 原生实现 → windowStage.loadContent("pages/Index")
④ Index.ets 创建 XComponent(SURFACE, libraryname:'SDL3')
⑤ Surface 就绪 → SDL_OpenHarmonyMainSurfaceCreated()
       → SDL_RunApp(..., RunAppOpenHarmonyMain, ...)
⑥ RunAppOpenHarmonyMain:
       dlopen("libmain.so", RTLD_NOW|RTLD_LOCAL)      SDL_sysmain_runapp.c:54
       dlsym("SDL_main")                              找不到则：
       dlsym("SDL_AppInit"/"SDL_AppIterate"/…)        SDL_sysmain_runapp.c:60-90
⑦ 进入我们的 SDL_AppInit / Iterate / Event / Quit
```

**实测差异**：鸿蒙的 `libmain.so` 只导出 `SDL_App*`、**没有 `SDL_main`**，
所以实际走的是回调兜底路径（功能不受影响）。

**与 Android 的关键差别**：Android 上 `libmain.so` 由 **Java 主动加载**；
鸿蒙上没有任何 ArkTS 代码加载它，**只能等 SDL 的 `dlopen`**。

### 8.7.4 `dlopen` 本身：同一 API，两套 libc

| | Android | HarmonyOS |
|---|---|---|
| libc | **bionic** | **musl 系** |
| 加载器 | `/system/bin/linker64` | 系统动态链接器 |
| 命名空间 | ✅ Linker Namespace（限制可加载路径） | ❌ 无此机制 |
| 裸名解析 | 按命名空间搜索路径 | 按应用库目录 |
| 本仓库 `libmain.so` 的 NEEDED | `libSDL3_ttf, libSDL3, libm, libdl, libc` | `libSDL3_ttf, libhilog_ndk.z, libSDL3, libc++_shared, libc` |

注意鸿蒙多了 `libc++_shared.so` 与 `libhilog_ndk.z.so` —— 两边的 C++ 运行时策略与系统库不同。

`RTLD_LOCAL` 的语义两边一致：`dlsym(handle, …)` 仍会搜索该句柄的依赖链，
所以 SDL 用 `RTLD_NOW | RTLD_LOCAL` 打开 `libmain.so` 后能正常解析入口。

### 8.7.5 静态化可行性矩阵

| 平台 | SDL3 本体 | SDL3_ttf / 应用代码 | 能否合并成单库 | 入口解析方式 |
|---|---|---|---|---|
| **iOS** | 可静态 | 可静态 | ✅ 本来就是单可执行文件 | 链接期 |
| **Android** | 可静态（需覆盖 `getLibraries()`，非常规路径） | 可静态 | ⚠️ 理论可行，需实测 JNI/符号 | `dlopen` + `dlsym` |
| **HarmonyOS** | ❌ 必须独立 `libSDL3.so`（NAPI 契约） | 可静态进 `libmain.so` | ❌ 需改 SDL 或留桩 | `dlopen` + `dlsym` |

**鸿蒙为什么不能合并**：两条硬编码互相冲突 ——

1. NAPI 模块名 `"SDL3"` 写死在 C 里，ArkTS 必须 `import 'libSDL3.so'`
2. `dlopen("libmain.so")` 也写死在 C 里，必须是独立文件

### 8.7.6 落地建议

| 平台 | 建议 | 原因 |
|---|---|---|
| iOS | 保持全静态单二进制 | 已是最简，无运行期查找 |
| Android | 保持现状（3 个 `.so`） | 官方路径，稳定 |
| Android（可选） | 覆盖 `getLibraries()` 合并成单 `.so` | 减少文件，但属非常规路径，需回归测试 |
| HarmonyOS | 只做「应用代码 `.a` + 薄壳 `libmain.so`」 | 不改任何契约，零维护成本 |
